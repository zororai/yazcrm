# Data Collection & Analytics

KoboToolbox-style data collection for YAZ CRM. Forms are designed as XLSForms, the beneficiary app (`yazcrm_beneficiary_flutter`) fills them in offline and syncs them to `/api/v1`, and staff analyse, validate, export and map the data in the CRM under **Data Collection**.

## Setup

1. Run the migrations:

   ```bash
   php artisan migrate --force
   ```

   - `2026_10_30_000001_reshape_data_collection_for_xlsform` rebuilds the old (empty) submission, assignment and review tables. It refuses to run if any of them hold data.
   - `2026_10_30_000002_create_jobs_table` adds `jobs`, `job_batches` and `failed_jobs`.
2. Set these in `.env`:

   ```dotenv
   QUEUE_CONNECTION=database              # exports and CRM mapping run in the background
   DATA_COLLECTION_MEDIA_DISK=local       # or s3 to keep photos off the server
   DATA_COLLECTION_MEDIA_MAX_KB=5120      # largest photo accepted (5 MB)
   DATA_COLLECTION_EXPORT_DISK=local
   DATA_COLLECTION_RATE_LIMIT=120         # app requests per minute per device (×3 per user)
   SANCTUM_EXPIRATION_MINUTES=43200       # app/API tokens last 30 days; 0 = never expire
   ```

   Then run `php artisan config:clear`.
3. Build the frontend with `npm ci && npm run build`. Leaflet and markercluster are new dependencies.
4. Optionally, add the sample form and a test enumerator:

   ```bash
   php artisan db:seed --class=DataCollectionSampleSeeder
   ```

   This deploys **Household Survey (sample)** and creates `enumerator@example.test` / `enumerator123`, who is assigned to collect it. Running it again is safe.

### Queue worker

Exports, the CRM mapping and the analytics projection run as queued jobs. With `QUEUE_CONNECTION=sync` they still work, but inside the web request, so large exports can time out. On the server, keep a worker running with systemd.

`/etc/systemd/system/yazcrm-queue.service`:

```ini
[Unit]
Description=YAZ CRM queue worker
After=network.target mysql.service

[Service]
User=www-data
Group=www-data
WorkingDirectory=/var/www/yazcrm
ExecStart=/usr/bin/php artisan queue:work --sleep=3 --tries=3 --max-time=3600 --timeout=1800
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Enable and start it:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now yazcrm-queue
```

After each deploy, run `php artisan queue:restart` so the worker loads the new code. Failed jobs are listed by `php artisan queue:failed` and retried with `php artisan queue:retry all`.

### Scheduler

The existing `schedule:run` cron is enough. This module adds `sanctum:prune-expired --hours=24` (daily), which clears expired app tokens.

### Storage

- **Photos:** stored on `DATA_COLLECTION_MEDIA_DISK` under `data-collection/{form}/{submission}/{uuid}.{ext}`. The name is generated by the server and the type is detected from the file's bytes. Photos are only served through `/data-collection/media/{id}`, after an access check.
- **Uploaded XLSForms:** `storage/app/private/data-collection/xlsforms/`.
- **Exports:** stored on `DATA_COLLECTION_EXPORT_DISK` under `data-collection/exports/`. Only the person who asked for an export can download it.

On S3, set the usual `AWS_*` variables and change the disk names to `s3`.

## Roles and access

| Data-collection role | How it's granted | Can |
|---|---|---|
| Admin | CRM role `admin` or `director` | Everything |
| Form Designer | Nav permission **Data Collection: Form Designer** | Upload, deploy and assign every form, plus every per-form permission |
| Enumerator | Per-form assignment with *collect* | See the form in the app and send submissions |
| Analyst | Per-form assignment with *view, edit, export* | Data table, reports, validation, edits, exports |
| Viewer | Per-form assignment with *view* | Read-only data and reports |

- **Assignments:** made on the form's page, to people or to everyone with a CRM role. *map* gives access to the CRM mapping screen.
- **Personal data:** fields with `pii = yes` in the XLSForm are masked (`•••`) everywhere unless the user is an admin or has the nav permission **Data Collection: see personal data (PII)**. That covers the table, search, the submission page, the audit trail, exports and the feed.
- **Deletes:** always soft, and only admins and designers can delete. Every change is written to `data_collection_submission_audits`.

## XLSForms

- **Workbook:** sheets named `survey`, `choices` and `settings`. The form's page has a blank template and the sample household survey to download.
- **Supported types:**
  - Questions: `text`, `integer`, `decimal`, `select_one list`, `select_multiple list`, `date`, `time`, `datetime`, `geopoint`, `image`/`photo`, `note`, `calculate`
  - Structure: `begin/end group`, `begin/end repeat`
  - Metadata rows (`start`, `end`, `deviceid`…) are accepted and ignored.
- **Supported columns:**
  - `label`, `hint`, `required`, `required_message`, `relevant`, `constraint`, `constraint_message`
  - `calculation`, `default`, `appearance`, `choice_filter`, `repeat_count`, `read_only`
  - `pii` (this one is a YAZ extension)
  - `label::Language (code)` for translations
- **Expressions:**
  - Field references: `${field}` and `.`
  - Operators: `= != < <= > >=`, `and or`, `+ - * div mod`
  - Functions: `if()`, `selected()`, `count-selected()`, `selected-at()`, `count()`, `sum()`, `min()`, `max()`, `today()`, `now()`, `concat()`, `contains()`, `starts-with()`, `ends-with()`, `substr()`, `string-length()`, `regex()`, `coalesce()`, `round()`, `int()`, `number()`, `not()`
- **Upload checks:** each upload is checked for duplicate names, unknown types, missing choice lists, unbalanced groups or repeats, and invalid or broken expressions. Problems are listed by sheet, row and column, and a version with problems can't be deployed.
- **Versions:** uploading creates a draft version, or replaces the current draft. Deploying makes it the version the app downloads and archives the previous one. Archived versions still accept submissions from devices that haven't updated, and every submission keeps the version it was filled in on.

## App API (`/api/v1`)

The app uses the same Bearer token as `POST /api/auth/login`. Its response includes `user.id` and `user.name`.

| Endpoint | Purpose |
|---|---|
| `GET /forms` | Deployed forms the user collects for: `id, title, version, checksum, updated_at` |
| `GET /forms/{id}/schema?version=` | Form schema with inline choices. 403 if not assigned, 404 if the form or version is missing |
| `POST /submissions/batch` | Up to 50 items. Always 200 with per-item `accepted / duplicate / rejected`. 422 only for a malformed envelope |
| `POST /submissions/{client_uuid}/media` | Multipart `field_name` (or `field`), `file`, optional `filename`. 404 until the submission is accepted. Idempotent per field and filename |
| `GET /sync/status` | `server_time`, current form versions, and `accepted_client_uuids` when `since` or `client_uuids` is given |

- A 401 always carries `{"code": "token_expired" | "unauthenticated"}`.
- A 429 carries `Retry-After`.
- Data problems are never a 5xx: they come back as a `rejected` item with `errors: [{field, message}]`.
- Full request and response samples are at `/api/documentation` (Swagger, tag *Data Collection v1*). Regenerate them with `php artisan l5-swagger:generate`.

## Analytics and the feed

- **Form tabs:** each form has **Data**, **Summary**, **Map**, **Dashboard** and **CRM mapping** tabs. They share one filter bar (dates, enumerator, status, search, question = answer), and exports use the same filters.
- **How reports are computed:** they run on `data_collection_submission_values`, a flattened and indexed copy of each answer that the queued job rebuilds after every accept or edit. To rebuild it for older data, re-run the mapping from the CRM mapping tab, or dispatch `App\Jobs\DataCollection\ProcessSubmission` for each submission.
- **Exports:** CSV, XLSX (one sheet per repeat), GeoJSON and a PDF summary. They are queued, and the bell says when the file is ready.
- **Power BI / Excel feed:** `GET /api/data/forms/{id}/submissions` returns OData-style JSON (`value`, `@odata.count`, `@odata.nextLink`, `$top`/`$skip`). `GET /api/data/forms/{id}/submissions.csv` returns CSV. Both accept a Bearer token, or HTTP Basic with the CRM email and password. They need the **Data API** permission, and PII is masked as above.

## CRM mapping

On the **CRM mapping** tab, choose a target (beneficiary profile, contact, case or beneficiary activity), a mode, and which question fills each CRM field:

- **Create:** makes a new record. If an existing record matches the key field, it is logged as a duplicate and linked instead.
- **Update:** updates the record that matches the key field. If nothing matches, the submission is skipped.
- **Store only:** does nothing.

Mapping runs in the background. Each result (created, updated, duplicate, skipped or failed, plus the error and the number of attempts) appears in the **Sync log**, which has **Retry failed** and **Re-run for all**. Re-running updates the linked record rather than creating another, and a mapping failure never affects the stored submission.
